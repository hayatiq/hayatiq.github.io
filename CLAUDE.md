# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Hayatiq is a static, single-page e-commerce marketing site for a handmade natural-wellness product brand (Bangladesh). There is no build step, no package manager, and no backend — it's plain HTML/CSS/JS deployed as static files (to Netlify, per the canonical URL in `index.html`). Routing uses real paths via the History API (e.g. `/product/conditioner-bar`), not hash fragments — `_redirects` (`/* /index.html 200`) is what makes Netlify serve `index.html` for those paths instead of 404ing, and `<base href="/">` in `index.html` is what keeps every `./`-relative asset reference (its own CSS/script tags, every product image path) resolving against the site root instead of the current route's path.

## Development

There is no build/lint/test tooling in this repo. To develop, just open/serve `index.html` directly, e.g.:

```bash
python3 -m http.server 8000
```

Then browse to `http://localhost:8000`. Reload the page after editing any file — there's no hot reload.

Anywhere except the live address (`hayatiq.netlify.app`) the site runs in **test mode** (`js/config.js`): a yellow banner shows, and order/contact forms, Telegram alerts and visit-summary emails go through their normal flow but send nothing (they log what they would have sent to the console). So local, phone-over-Wi-Fi and Netlify preview testing never uses FormSubmit quota or pings Telegram.

To test real sends locally, `node tools/dev-server.js` serves the site with SPA fallback and runs `netlify/functions/order.js`, reading secrets from a git-ignored `.env` (template: `.env.example`); opening the site with `?send=real` switches that tab (sessionStorage) to real sends, only on localhost/private-network hosts (`IS_LOCAL`/`LOCAL_REAL_SENDS` in `js/config.js`). The server also passes the `.env` `SEND_*` switches to the page (`window.HAYATIQ_LOCAL_SWITCHES`); every send checks `sendsOn(kind)` (a `NOTIFY` key) rather than `IS_LIVE`, and a local test order stores a per-channel `report` (`deliveryReport()` in `js/partial.js`) shown on `/order`. Never put tokens in the code — the repo and site are public.

`python3 -m http.server` (and VS Code's Live Server extension, the other common way to preview this repo) has no SPA fallback, so either one 404s ("Cannot GET /product/...") if you type/paste/refresh a nested path directly (e.g. `/product/solid-conditioner-bar`) — it's looking for a real file at that path and there isn't one. Clicking through the app itself is unaffected, since that's all client-side routing (see the router in `js/script.js`), and it won't happen on the real Netlify deployment either (`_redirects` handles the fallback there). To test deep links/refreshes on nested paths locally the way Netlify serves them in production, run `npx serve -s .` instead and browse to the port it prints.

## Architecture

Everything is driven from eight plain scripts loaded at the end of `<body>` in `index.html`, in this order: `js/config.js`, `js/icons.js`, `js/visitor.js`, `js/products.js`, `js/invoice.js`, `js/script.js`, `js/partial.js`, `js/i18n.js`. None of these use ES module syntax — they're classic `<script>` tags that share one global scope, which is how `js/script.js` can reference `PRODUCTS` without an explicit import.

### `js/products.js` — product data
Just the `PRODUCTS` array (plus the small `PLACEHOLDER_WARNS`/`PLACEHOLDER_STORAGE` constants it uses) and the `display_order` sort — kept separate from `js/script.js` so editing the catalog (listing, pricing, images) never requires touching rendering code. Loaded before `js/script.js` so `PRODUCTS` is a defined global by the time any render function runs. See "Adding a product" below.

### `js/script.js` — app core
- **Path-based SPA router** (`navigate()`): all "pages" are `<section id="view-*">` elements in `index.html` that get shown/hidden by toggling an `active` class based on `location.pathname` (`/`, `/products`, `/product/:slug`, `/categories`, `/contact`, `/about`, `/cart`, `/checkout`, `/order`, `/wishlist`). The `/products` route also reads `?cat=` and `?concern=` query params to filter the grid; the category chips above it (`setupProductFilters()`) are plain links to those URLs. A document-level click listener intercepts clicks on same-origin `href="/..."` links and drives them through `history.pushState` + `navigate()` instead of a full page load (`goTo(path)`); the browser back/forward buttons fire a native `popstate`, which also calls `navigate()` directly. `navigate()` dispatches a `route-changed` `CustomEvent` on every call (initial load, link click, or popstate) — `js/visitor.js` listens for that instead of `hashchange` to track page views. `setPageMeta()` updates `<title>`, the description/keywords meta tags, `<link rel="canonical">`, and the Open Graph/Twitter tags per route, using each route's real path so every page gets its own canonical URL instead of all pages pointing at the homepage. Any path that isn't a known route, or a `/product/:slug` that doesn't match a real product, renders `#view-notfound` (`renderNotFound()`) instead of silently falling back to the homepage or the wrong product — that view's meta tags are set to `noindex, nofollow` (the server still returns HTTP 200 for it either way, since Netlify's `_redirects` fallback has no way to return a real 404 status without a serverless function).
- **`PRODUCTS` array**: the entire product catalog, defined in `js/products.js` (see above) — no CMS/database.
- **`TESTIMONIALS` array**: site-wide (not per-product) social proof — Messenger/Facebook screenshots or general feedback not tied to one SKU. Ships empty; `renderTestimonials()` hides the homepage "Customer Love" section entirely while it's empty. Only add genuine feedback, with the customer's permission.
- **Homepage sections** (`#view-home`, in order): top section, chosen by `HOME_HERO` in `js/config.js` (both are in `index.html`, marked `data-hero`): `"text"` is the original headline plus one trust line (`#trustLineText`), `"photo"` is a photo hero with a Shop Now button plus trust chips (`#trustLine`); delivery charges and times come from `js/config.js` → Shop by Category (photo tiles, a sideways row on phones, plus "Shop by need" chips from the `concern` entries of `NEED_TILES`/`renderNeedTiles()`, matched against each product's `concerns` array) → Best Sellers (carousel, `renderTopProducts()`/`topProducts()` — strictly opt-in: shows only products with `topSelling: true`, no automatic fallback, and the whole section hides itself when nothing is marked) → Customer Love (carousel, `renderTestimonials()`) → Shop Our Products (grid of 8, `renderFeatured()` — skips products already in the Best Sellers carousel) → How to Order (4 steps) → FAQ → Why HAYATIQ (photo card with the contact prompt).
- **Products still on the placeholder photo** (`hasRealPhoto()`): kept off the homepage and "You may also like", listed last on `/products`, and shown as a brand-colored tile with the name (`photoPendingTile()`) instead of the placeholder picture.
- **Category/need availability**: categories and need tiles are never hidden, even at zero live products — `liveProductCount()`/`renderCategoryAvailability()` label each with a live count or "Coming Soon", and an empty category/need page shows a "Notify Me" Messenger banner (`notifyMeLink()`, `ref=notify-{topic}`).
- **Rendering**: functions like `renderFeatured`, `renderTopProducts`, `renderNeedTiles`, `renderProducts`, `renderDetail`, `renderTestimonials`, `renderCart`, `renderCheckoutItems` build HTML strings and inject via `innerHTML` directly into DOM containers (`featuredGrid`, `topProductsGrid`, `needTilesGrid`, `productsGrid`, `detailWrap`, `testimonialGrid`, `cartItems`, `checkoutItems`). Inline `onclick="..."` handlers (e.g. `addToCart('id')`) are used throughout instead of addEventListener-based delegation for dynamically rendered markup. The two homepage carousels (Top Selling Products, Customer Love) are plain CSS scroll-snap, driven by a shared `scrollCarousel()` helper (`scrollTopProducts()`/`scrollTestimonials()` wrappers) — no JS carousel library. Top Selling Products cards use a distinct `.product-card-carousel` sizing class (`productCard(p, { carousel: true })`) from the regular grid cards, since they're laid out for horizontal scrolling rather than a grid.
- **Product card badges** (`BADGE_TYPES`, `productCard()`): `badge` field (`"hot"`/`"new"`/`"sale"`/`"popular"`) shows a fixed-color badge; `topSelling: true` auto-applies a gold "Best Seller" badge when no explicit `badge` is set — the same field that puts the product in the Top Selling Products carousel. Coming-soon cards show an "Ask about this" Messenger button instead of a badge/wishlist control.
- **Image lightbox** (`openImageLightbox()`/`closeImageLightbox()`, `#imageLightbox` in `index.html`): shared full-size viewer for the product detail gallery image and any review/testimonial photo; closes on backdrop click, its ✕ button, or Escape (shared `keydown` listener with the cart drawer).
- **Cart & reviews persistence**: both use `localStorage` directly (`hayatiq_cart`, `hayatiq_reviews` keys) — there is no server-side cart/order storage. Per-product reviews (`reviews: []` on a product) support optional `image`/`source` fields for photo proof and provenance (e.g. `"Messenger"`).
- **Product images**: every photo in `images/` has a 600px-wide copy in `images/cards/` with the same file name; `cardImage(src)` maps one to the other. Cards, thumbnails and cart rows use the card copy; only the product page's main photo loads the full file (capped at 1,100px). A new photo needs both files.
- **Product page**: one square photo that swipes, with a "2 / 3" count and square thumbnails below (`setupGallery()`); an optional `benefits` list shows as ticks under the description. "Order Now" (`orderNow()`: adds the item once and goes to `/checkout`) plus "Add to Cart"; every add shows a `toast()` with a Checkout link and bounces the cart icons (`bumpCart()`), and the bottom cart bar (`#floatingCartBtn`, `updateFloatingCartButton()`) appears whenever the cart isn't empty. Once a product page's own buttons scroll out of view, a slim Order Now bar (`#orderBar`, `watchOrderBar()`) takes the cart bar's place. On phones the header sticks to the top. "You may also like" (`relatedProducts()`/`renderRelated()`) shows the product's `related` ids first, then same-category products, then top sellers, up to 4.
- **Checkout** (`initCheckout()`): `normalizePhone()` accepts Bangla digits, +88/88 prefixes, spaces and dashes; the delivery area has no default; the Place Order button shows the total. After submitting, the order (with its `HQ-YYMMDD-XXXX` number) is saved under `hayatiq_last_order` and `/order` (`renderOrderPage()`) shows the confirmation, or a "send it on Messenger" fallback if every channel failed (the cart is kept in that case).
- **Notices**: `toast(msg, type, action)` is a small built-in notice (no SweetAlert2).

### `js/config.js` — live vs test mode
The one place for shop-wide settings: `LIVE_HOSTS`/`IS_LIVE` (test mode), `NOTIFY` (who gets what: `business`/`developer` email addresses, and per message kind — `orderEmails`, `contactEmails`, `visitSummaryEmails`, `orderTelegram`, `contactTelegram` — a list of those roles; `orderSheet` on/off; `recipients(kind)` turns a list into addresses), `UMAMI_WEBSITE_ID` (analytics, off while empty), `HOME_HERO` (homepage top section), `DELIVERY_TIME`, `DAMAGE_PROMISE`, and the Messenger/Facebook links. Every real send checks `IS_LIVE` (`sendEmails()`/`sendToServer()` in `js/partial.js`, `flushVisit()` in `js/visitor.js`, `trackEvent()` here); any other host gets a test-mode banner and simulated success. It also redirects the GitHub Pages copy (`hayatiq.github.io`) to the Netlify site, and records the visit's source (`visitSource()`/`sourceLabel()`: landing page, referrer, `utm_*` tags) for visit emails and orders. Secrets stay in Netlify environment variables. If the shop moves to its own domain, add it to `LIVE_HOSTS`; `netlify/functions/order.js` compares the request origin with Netlify's own `URL`.

### `js/invoice.js` — order invoice
`invoiceHtml(order)` renders the dashed invoice card on `/order` (used by `renderOrderPage()`); `downloadInvoice()` draws the same invoice on a canvas (`drawInvoice()`, A4 width, 3× scale) and wraps the JPEG in a hand-built one-page PDF (`imagePdf()`), so there's no PDF library. Loaded before `js/script.js` because the router can render `/order` on first load; uses `money()`/`escapeHtml()`/`toast()` from `script.js` at call time.

### `js/i18n.js` — Bangla preview
A বাংলা/EN switch in the header, shown only off the live address for now. In Bangla mode it swaps the page's text in place (like `js/icons.js` swaps icons): interface text from `BN`/`BN_PATTERNS`, product text from each product's `bn` block in `js/products.js` (paired piece by piece with the English, so a `bn` field must keep the English shape: same list order, same `<b>`/`<i>` tags, same number of `;` steps in `how`). Data, emails, Telegram, the sheet and the PDF invoice stay English; prices keep English digits (৳850).

### `js/icons.js` — inline SVG icons
Replaces the Font Awesome icon font: markup keeps Font Awesome class names (`<i class="fa-solid fa-heart">`), and a MutationObserver swaps each for an inline `<svg class="icon">` from the `ICONS` map, including markup rendered later via `innerHTML`. A new icon needs its path added to `ICONS`.

### `js/visitor.js` — behavioral analytics
Tracks one visit per browser tab (refreshes and app switches continue it) in `sessionStorage` (`current_visit_data`), keeping the last 10 in `localStorage` (`user_behavior`). The visit starts when the script loads, before the router records the landing page. `flushVisit()` runs on tab-hide/`pagehide` and emails a summary via FormSubmit (`keepalive` fetch) only if something new happened since the last email (`visitSignature()`); live address only (`sendsOn()`), sent to `NOTIFY.visitSummaryEmails`, never from a `?notrack` device (`NO_TRACK` in `js/config.js`). At most `VISIT_EMAIL_LIMIT` (2 per 10 min) per device, logged in `localStorage` `hayatiq_visit_email_log`; a held-back visit gets `pendingEmail: true` and is sent later by the next flush or by `sendHeldBackVisits()` (from the visit history, 5 s after load, within a day). Each flush stores a `cartNow` snapshot (`cartSnapshot()`, using `orderItems()` from `script.js`). Cart events are recorded by `addToCart()`/`removeFromCart()`/`clearCart()` in `script.js` with product names. When editing checkout/product flows, be aware this file listens for the same `route-changed` event (see `js/script.js`'s router) and DOM elements as `script.js`.

### `js/partial.js`
Wires the contact and checkout form `submit` handlers. An order gets a number (`newOrderId()`), then the emails (`sendEmails()` → FormSubmit, one per recipient in `NOTIFY.orderEmails`, in parallel) and the Telegram/Sheet call (`sendToServer()` → `netlify/functions/order.js`) go out in parallel; the order counts as received if any channel succeeds. Rate limiting via `localStorage` timestamps (contact: 3/hour, orders: 5/20min; test sends don't count).

### `netlify/functions/order.js` and `google-apps-script/orders.gs`
The function also forwards contact-form messages (`{ kind: "contact" }`, from `sendContactToServer()` in `js/partial.js`; the form counts as sent if the email or Telegram gets through). For orders it validates the order (phone, items, field lengths), sends the Telegram alert (HTML parse mode with escaping, Dhaka time) and posts a row to the Google order sheet, depending on the channels the browser passes from `NOTIFY`. Telegram recipients are named `business` (`TELEGRAM_CHAT_ID`) and `developer` (`TELEGRAM_DEV_CHAT_ID`, optional own bot `TELEGRAM_DEV_BOT_TOKEN`) in `TELEGRAM_CHATS`; other secrets: `TELEGRAM_BOT_TOKEN`, `SHEET_WEBHOOK_URL`, `SHEET_TOKEN`; a channel with missing variables reports `"not-configured"`. `orders.gs` is the Apps Script web app pasted into the sheet (status dropdown, duplicate-order guard, repeated-phone highlight). Setup steps are in README.MD.

### Styling
`css/style.css` defines the design system as CSS custom properties at the top (`--color-earth`, `--color-almond`, `--color-night`, `--radius`, `--shadow-soft`, etc.) — reuse these tokens rather than hardcoding new colors/shadows.

### External dependencies (all via CDN, no npm)
Only Google Fonts (Outfit, Lora), plus the optional Umami analytics script once `UMAMI_WEBSITE_ID` is set.

## Adding a product

Products live only in the `PRODUCTS` array in `js/products.js` (not `js/script.js` — that file only renders them). All keys are required on every product object: `id`, `name`, `slug`, `price`, `category`, `images`, `short`, `ingredients`, `how`, `tips`, `warns`, `storage` (`subtitle`, `concerns`, `badge`, `topSelling`, `display_order`, `related`, `seoTitle`, `metaKeywords`, `benefits`, `bn` are optional; `ingredients`/`how`/`tips` may be left as `[]` when real content isn't ready yet — `renderDetail()` skips rendering a section entirely when its array is empty rather than showing an empty accordion). Notes:
- `slug` is now the product's real URL path (`/product/<slug>`, see the router in `js/script.js`), not just an internal identifier — avoid changing an existing product's slug once it's live, since that changes its URL and breaks any existing Messenger ref links/bookmarks/search listings pointing at the old one.
- `seoTitle`/`metaKeywords` (optional strings): override the `<title>`/meta-keywords tag on that product's detail page (`setPageMeta()` in `js/script.js`); both fall back to `${name} — Hayatiq` / the site-wide default keywords when unset. The product's own `short` field is always what's used as the meta description — there's no separate field for that.
- `benefits` (optional, up to 3 short strings): ticks under the product page description; word them from the product's own copy.
- `bn` (optional): the Bangla version of the product's text for `js/i18n.js` (see above).
- `related` (array of product ids, optional): shown first in that product's "You may also like" section; same-category products and top sellers fill the rest.
- `images`: put each photo in `images/` (max ~1,100px wide, WebP) and a 600px-wide copy with the same name in `images/cards/`.
- `display_order` (number, optional): a single `PRODUCTS.sort(...)` call at the end of `js/products.js` sorts the whole catalog by this field once at load (ascending, unset/non-numeric treated as last, ties keep array order since `Array#sort` is stable) — every render function that reads from `PRODUCTS` (`renderFeatured`, `topProducts`, `renderProducts`, `renderWishlist`) inherits the order for free, so a new listing surface never needs its own sort logic.
- `price`: a number makes the product live/purchasable; the string `"Coming Soon"` disables the buy button and shows a coming-soon detail view instead (see `isComingSoon` checks in `productCard`/`renderDetail`).
- `category` must match one of the categories rendered in the `#view-categories` section of `index.html`; add a new category block there if introducing one.
- `concerns` (optional array, e.g. `["Better Sleep", "Muscle Recovery"]`) drives the homepage "Find the Right Product" tiles — base tags on the product's own `how`/`tips` guidance, not guesswork; add a matching entry to `NEED_TILES` if introducing a new tag.
- `how` entries use a `"Tab Name: point one; point two;"` string format parsed by `renderHowToUseTags()` into tabbed panels — keep the `:` and `;` delimiters when adding entries.
- Messenger buttons link to `https://m.me/hayatiq.life?ref=<slug>` (product detail) or `ref=notify-<category>` (category/need "Notify Me" links) — the ManyChat automation on that account keys off this `ref` parameter (see README.MD for setting up new automations per product/ref).
